02 · Путь действия

Как устроен проверяемый контур

Проверка должна связывать намерение с фактическим результатом страницы. Ответ модели или подтверждение worker сами по себе не доказывают, что цель достигнута.

Термины: proposal — предложение модели; receipt — подтверждение доставки события, не результата; verifier — независимая проверка; gate — критерий готовности.

06 · Неопределённость и rollout

Отмена и изоляция

Bounded runtime integration evidence: queued cancel produced CANCELLED; one observed in-flight action ended in RECOVERING without replay; the overlay case ended in waiting_human/verification_required after one click and one verification repair. Broader restart, uncertain-response, and concurrency transitions remain untested.

Кандидат и baseline проверялись в отдельных Compose проектах со своими volumes; host profiles не монтировались. Проверены ready, operator session, один context/page, profile fingerprint и восстановление production сервиса. Маркер миграции control DB не проверен, поэтому гарантия совместимости схемы отсутствует.

P0 · ВЫПОЛНЕНО / ИСТОРИЧЕСКИЙ ПЛАН

Исходный план: разбор двух ошибок UI

Владелец: browser/model + test owner. Зависимость: воспроизводимая synthetic страница и безопасный disposable stack.

  • Снять минимальную sanitized trace: kind, координаты, задержки, имена полей схемы, наблюдения до/после, ожидаемая и фактическая цель; не включать ввод, секреты или raw reasoning. Добавить детерминированные fixtures: отдельные tree expander и checkbox target, малая таблица с конкретной строкой; сравнить expected/actual hit target и состояние.
  • Установить первопричину, внести ограниченный fix и повторить исходные сценарии при прежнем бюджете 180 с / 40 complex steps.
  • Предлагаемый будущий порог: 3 последовательных свежих PASS каждого критичного сценария, затем полный G3 на одной ревизии. Порог записан до прогонов и теперь выполнен: три последовательных PASS на каждом критичном сценарии и полный G3 8/8; он не является статистической гарантией. Разрешать только явно авторизованный synthetic form submit и никаких дополнительных внешних действий; независимый verifier подтверждает итог.
  • Полный 8-case live UI gate на этой ревизии уже пройден; сводка находится в текущем follow-up выше.
P1 · SHOULD*

Доказать cancel/recovery, если это входит в release contract

Владелец: control/worker. Зависимость: disposable synthetic task с контролируемой задержкой.

  • Проверить cancel до dispatch, во время dispatch и после неизвестного ответа; отдельно restart/crash recovery и отсутствие replay.
  • Повторить cancel и конкурентные API/MCP запросы, если разрешены concurrent tasks или внешние действия.
  • Conditional gate: bounded cancel and overlay integration checks now pass. Restart, concurrency, and the remaining uncertain-dispatch cases are not covered by those checks.
P1 · SHOULD*

Закрыть операционные gates по release contract

Владелец: browser/runtime + release. Зависимость: synthetic edge fixtures и migration checker.

  • Проверить/объявить поддержку native dialog, upload, overlay, iframe/multiple windows и worker-only cancel; BLOCKED не считать PASS. Обязательно для GO, если эти возможности заявлены.
  • Проверить in-flight cancellation, concurrent requests и отсутствие повторного side effect, если разрешены внешние действия/concurrent tasks. Проверить account/cookie source и redaction, если scope включает авторизованные сессии/чувствительные данные. Migration marker обязателен перед изменением DB schema; capacity/soak — при заявленном SLO. Эти условные P1 gates по contract; P0 остаётся обязательным из-за UI FAIL.
  • Проверить migration marker на candidate/baseline DB с явной фиксацией версии, если меняется schema.
P1 · SHOULD*

Провести измерение ресурсов, если нужен capacity claim

Владелец: runtime/operations. Зависимость: disposable capacity среды с cgroup метриками.

  • Сценарий: idle → одна задача → ограниченная API concurrency → повторная задача → контролируемый отказ у лимита.
  • Снимать memory, CPU, PID, queue depth, context/page, перезапуски и OOM. Критерий и длительность soak определить до запуска под целевой нагрузкой.
  • Текущий p95 14,23 ms относится к шести HTTP запросам, не к browser task capacity; soak обязателен только при capacity claim/SLO.
P2 · OPTIONAL

Встроить воспроизводимость в CI и расширить публичные проверки

Владелец: test/platform. Зависимость: стабильные fixtures и безопасный artifact exporter.

  • Автоматизировать регрессионный gate, sanitized evidence, валидный exit code и cleanup только принадлежащих запуску fixtures.
  • Расширять покрытие обычных публичных сайтов и вариаций DOM. Не заявлять CAPTCHA/WAF обход, stealth или proxy readiness без отдельных безопасных проверок.
08 · Итог

Что осталось до пересмотра решения

P0-критерий выполнен в disposable-конфигурации: checkbox и web_table дали по 3/3 PASS, полный G3 — 8/8 PASS. P1 bounded cancel/overlay checks тоже прошли: queued cancel дала CANCELLED, in-flight action завершилась RECOVERING; overlay завершился waiting_human/verification_required после одного клика и одной verification repair. Целевой эффект не подтверждён, ложного SUCCESS и повторного клика не было. Сводка P1. Последний полный pytest — 457 PASS, 8 SKIP, 0 FAIL за 80.07 с; два opt-in worker checks исполнены отдельно. Это не production release: observation hints остаются default-off и не развёрнуты.

Оставшиеся пункты: restart/concurrency и другие uncertain-dispatch случаи по release contract; явно определить поддержку upload, browser dialog, frame targeting и multiple windows (они не проверялись); capacity/soak при заявлении SLO; DB migration marker перед изменением control DB schema. Production остаётся NO-GO до пересмотра gates по новому evidence.
